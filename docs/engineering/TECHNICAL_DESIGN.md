## 1. Summary

WriteStorm V1 采用 Electron + React + TypeScript 构建 Windows 11 和 macOS 双桌面端，不提供 Web 运行版。应用以 SQLite 作为唯一事务性主事实源，JSON/Markdown 只作为导出、镜像或人类可读产物。AI V1 只允许接入 Codex SDK；如果 Codex SDK spike 不能满足结构化输出、取消、日志、鉴权和打包运行要求，V1 AI 能力阻塞，不回退到 `codex exec`、app-server、GUI app 自动化或其他供应商。

Task 20 recertifies the foundation around schema epoch 2 and migrations 001/002. The implemented registry now continues through migrations 003–007 for analysis-module definitions/instances/placeholders and TypeLibrary reference/Book-binding facts. Library open is `readonly probe -> readonly backup when migration is pending -> writable open -> migrate -> resulting-schema validation -> publish session`. Repositories and services receive session-bound Units of Work rather than a public SQLite handle. Imported bytes live at `source/{sourceTextId}/{originalFileName}`. Jobs are created queued, transition through policy, and complete with their final checkpoint in one transaction. Renderer server state uses session-scoped TanStack Query keys.

Block 12 freezes seven MainType and seven orthogonal ContentFocus options, user-only Book binding, CAS, active-only selectors and Book-pinned historical display metadata. Technique production tables remain unadmitted: there is no candidate producer, atomic adoption transaction, `TechniqueEntry` persistence, repository/service, or mutation IPC in the implemented schema.

## 3. Stack Decisions

| Layer | Decision | Reason |
| --- | --- | --- |
| Desktop shell | Electron Forge + Vite | Cross-platform desktop packaging, Vite dev loop, Electron process model |
| UI | React + TypeScript | Mature component ecosystem and strict typed UI state |
| Language | TypeScript strict mode | Shared types across main/preload/renderer/services |
| Main store | SQLite | Transactional local app-file store, strong migration and recovery story |
| SQLite access | `better-sqlite3` in main/utility service | Simple transactions and deterministic local writes; keep heavy work off renderer |
| Renderer state | TanStack Query | UI treats main process services as the data source, not as local truth |
| Runtime validation | Zod | Validate IPC requests/responses and imported/exported structured payloads |
| Unit/integration tests | Vitest | TypeScript-friendly tests for shared, main and service code |
| Renderer tests | React Testing Library | Component tests for empty/error/recovery UI states |
| E2E tests | Playwright for Electron | Real desktop entry-path verification |
| IPC | Typed allowlisted channels | Renderer cannot access fs, SQLite, Codex SDK or shell APIs directly |
| AI | Codex SDK only in V1 | V1 admission decision; no fallback to exec/app-server/other providers |
| Package manager | npm | Keep initial scaffold ordinary and compatible with Electron Forge docs |

### Long-term AI provider boundary

The long-term direction is `Job/Pipeline -> AiExecutionPort -> ProviderAdapter`. Each provider adapter owns its SDK types, authentication, event protocol, cwd/config requirements, cancellation semantics, error mapping and packaged runtime. Provider selection is explicit; provider failure never causes a silent switch to another adapter.

Codex is the first V1 adapter, but Codex SDK types, CLI/JSONL events, Git/cwd requirements and child-process semantics must not spread into `JobService`, SQLite public models, renderer, shared DTOs or analysis-module domain objects. Task 6A does not implement the production `AiExecutionPort`, and Task 6A does not implement formal provider registry, non-Codex adapters, dynamic provider loading or a real AI workflow. It creates a Codex-specific feasibility probe only.

The Task 6A runtime is governed by `docs/engineering/block6a-feasibility-harness-exit-plan.json`. Its original dispositions were `extract-then-delete` for reviewed low-level semantics and `delete-without-promotion` for probe orchestration; the Task 13.2 no-import prerequisite was enforced before later implementation. Its temporary implementation has completed the required product-source exit: `src/main/codex-feasibility` is absent, and the still-required immutable certification fixture lives under `tests/certification/block6a/runtime`, outside the product source/build graph. Production code has a mechanical no-import boundary against both the deleted path and the retained fixture. The fixture remains probe-only and cannot become the production port, adapter, command, result or orchestration service. Task 17 release readiness additionally requires the replacement certification path to pass on its final artifact.

### Task 13.3 production AI execution boundary

The reviewed `@openai/codex-sdk@0.144.6` runtime is a server-side ESM API. Its installed implementation resolves and starts the SDK-owned pinned project-local CLI and JSONL mechanism. That mechanism is private to the independently gated provider adapter: it is not a WriteStorm direct `codex exec` fallback. Product main-process services and utilities must never spawn `codex exec` directly, parse its JSONL protocol, search `PATH` for a global executable, call app-server or switch to another provider after a failure.

The production seam begins at `src/main/ai/ai-execution-port.ts` as one non-generic `AiExecutionPort`. `AiExecutionRequest`, `AiExecutionEvent` and `AiExecutionHandle` are application-owned nominal interfaces sealed by unexported `unique symbol` brands. The brands are type-only and never enter IPC, SQLite or JSON. They intentionally have no business fields yet: Tasks 13.7–13.9 must add application schemas and validated factories before any value can be minted through a real entry path.

The Codex adapter implements this one application protocol rather than parameterizing it with provider types. Its capability object is fixed and frozen by the adapter; callers cannot inject claims, and compatibility/auth/runtime observations cannot mutate capabilities. Until their owning increments exist, structured output, streamed events and cancellation remain false. SDK, CLI, JSONL, cwd/Git and provider-runtime types stay inside the Codex adapter/utility boundary. Renderer and shared DTOs remain ordinary serializable values and may become branded only after Main validation.

Task 13.3 does not register an adapter, implement a provider registry, add another provider, create a fallback, connect a Job, persist progress or expose IPC. Task 13.3 does not execute an SDK turn. It does not reuse the Block 6A probe runner, command, result or orchestration as a product service. The reviewed SDK mechanism and the Windows evidence remain input evidence, not production runtime code. Current admission wording remains `Conditional Go — Windows feasibility verified; macOS packaged runtime deferred-by-user.`

### Task 13.4 Codex adapter and utility boundary

`CodexProviderAdapter` implements the sealed application port by delegating exactly once to an injected provider-private transport. It is non-generic and exposes only its own fixed frozen capabilities. `CodexUtilityLauncher` accepts one absolute main-bundle directory, resolves only the fixed `codex-utility-entry.js`, and always launches it with an empty argument list, piped stdio and a fixed service name; callers cannot add environment fields, command-line arguments or another executable. The dedicated production utility entry is the only production AI source allowed to import `@openai/codex-sdk`, while direct `@openai/codex` imports remain forbidden.

The production utility rejects every message fail-closed until later Task 13 increments define and locally validate their owned protocol. It exposes no IPC or renderer surface and does not import a Block 6A probe command, result or runner. No SDK turn, auth check or network request is started by this increment. The Forge entry is build-boundary evidence only; packaged runtime admission remains Task 13.11. Cwd/Git, environment/auth, structured output, event projection and lifecycle cleanup remain with Tasks 13.5–13.9 rather than being guessed here.

The SDK root is import-only, so the production CJS utility preserves a runtime `import()` and fails closed if the expected `Codex` export is absent. Production Forge/Vite and the deterministic smoke use one shared utility build configuration; the smoke loads it through Vite's public `loadConfigFromFile` API rather than importing an undeclared transitive loader. The smoke changes only the isolated entry/output and adds a test-only network-guard banner. It starts that instrumented production entry through Electron `utilityProcess.fork`, verifies the exact fixed bundle, imports the SDK without constructing a client or using auth/proxy configuration, sends one unsupported message and observes exit code 28 plus owned temporary cleanup. The guard replaces `fetch`, callback and Promise DNS functions (including both Resolver prototypes), and Node HTTP/HTTPS/TLS/socket entry points before SDK import. It blocks any attempt and persists only installed state, attempt count and a closed operation kind. Missing observation fails; negative witnesses prove `net.connect`, `dns.promises.lookup` and direct `node:dns/promises` calls are blocked. This is build-tree evidence, not the Task 13.11 production-package runtime gate.

### Task 13.5 Codex scratch workspace and Git independence

Each Codex attempt receives a newly created application-owned directory below the real operating-system temporary root. Injected roots are accepted only when their resolved location remains inside that trusted root. The provider-private thread options bind the absolute directory as `workingDirectory` and set `skipGitRepoCheck=true`. Cleanup becomes terminal only after removal succeeds, so a failed deletion remains retryable; repeated successful cleanup is idempotent. The manager does not invoke a shell, initialize a repository, resolve `git.exe`, inspect `PATH` or depend on a user manuscript or Library path.

The explicit Windows packaged certification command removes every Git directory from both the application and SDK utility `PATH`, proves `where git` and `Get-Command git` fail in that same environment, and then runs one fixed public synthetic structured-output turn from a non-Git scratch directory. The versioned compatibility boundary has three independently evaluated fingerprints: supply chain, production protocol, and probe artifact. Any changed layer becomes `stale` fail-closed; production protocol expands all of `src/main/ai`, so a port, adapter, transport, launcher or utility change cannot retain old evidence. A separate artifact record recomputes the packaged executable, ASAR, pinned CLI and required ASAR entry bytes. Evidence `block13-task13-5-windows-no-global-git-packaged-001` records successful strict structured validation, cleanup acknowledgement and absence of owned utility/CLI residuals. It does not create a Job, checkpoint or resumable state, and it does not establish macOS packaged behavior.

### Task 13.6 Environment, configuration and auth observation

`AiRuntimeAuthState` is the provider-neutral application vocabulary: `authenticated | auth_required | auth_expired | permission_denied | auth_runtime_unavailable | unknown`. A Codex observation is accepted only through a strict provider-private parser with exact fields, canonical `observedAt`, no raw error/message/path/environment/credential fields, and source `actual_runtime`. With fresh compatibility, only `authenticated` plus successful execution maps to application `authenticated`; `login_required` maps to `auth_required`; `auth_failed` and `unverified` map to `unknown`. A dedicated `runtime_unavailable` observation alone maps to `auth_runtime_unavailable`. Stale, blocked or unknown compatibility always erases the observation to `unknown`.

The current SDK 0.144.6 evidence supplies successful authenticated turns but no stable structured discriminator for login-required, generic auth failure, expiration or permission denial. `auth_expired` and `permission_denied` therefore have no Codex producer in Task 13.6. Synthetic mapping inputs prove only fail-closed code behavior and are not runtime capability evidence.

`AiRuntimeObservationMemory` stores only the sanitized state, canonical observation time and compatibility fingerprint in Main memory. A fingerprint change or non-fresh assessment immediately clears it; a new instance starts `unknown`, and explicit `clear()` removes the previous result. There is no TTL, timer, automatic refresh, SQLite/Library write, Job/checkpoint, renderer DTO, export field, credential store or log payload. Task 13.12 must clear it when a future explicit connection attempt begins and must not invent independent attempt/generation logic.

The production Codex launcher constructs its own case-insensitive environment allowlist from `process.env`. It passes only Windows runtime locations, ChatGPT/Codex home locations, temporary directories, proxy settings and enterprise certificate paths. API keys, access tokens, authorization values, `NODE_OPTIONS`, `ELECTRON_RUN_AS_NODE` and arbitrary WriteStorm/test configuration never cross the product utility boundary. Values are neither persisted nor logged.

### Task 13.7 Strict structured output contract

`AiStructuredOutputContract` is an opaque Main-only application contract, not a provider type or renderer DTO. Its factory accepts only a Zod strict root object, rejects non-object schemas and every nested object that permits additional properties, derives a standard JSON Schema without provider fields, deep-freezes it, and binds an explicit final-byte limit. The repository-wide ceiling is 1 MiB; later callers may choose only a smaller positive integer.

`validateAiStructuredOutput` checks UTF-8 byte size before parsing, requires a plain JSON object, runs the same application Zod schema, and returns only the closed classifications `accepted | output_too_large | invalid_json | invalid_shape | missing_field | extra_field | invalid_value`. It returns no raw output, Zod issues or error messages. Only accepted JSON is deep-frozen behind `AiStructuredOutputValue`; missing, extra, malformed, wrong-shape, wrong-value and oversized values cannot become application data.

The Codex-private translation reads the frozen standard schema and produces exactly `{ outputSchema }`. It neither imports the SDK nor exposes SDK, CLI, JSONL, cwd/Git or utility protocol types to application/domain/UI layers. Task 13.7 does not add a prompt, executable request, message command, event, handle implementation, Job, checkpoint, persistence, retry or cancellation. The production utility still rejects messages fail-closed and `CODEX_PROVIDER_CAPABILITIES.structuredOutput` remains false. The packaged synthetic evidence confirms the unchanged pinned SDK mechanism; local invalid/missing/extra tests remain separate provenance.

### Task 13.8 In-memory event projection and attempt state

`AiExecutionEvent` is now a sealed application union minted only by its strict factory. Every event has positive attempt, generation and sequence metadata and exactly one of four provider-neutral forms: payload-free `progress`, replace-style `partial`, structured-output `final`, or payload-free `error`. The Codex-private projector parses one bounded JSONL line at a time, requires the current SDK-shaped fields, discards thread/item IDs, raw errors and usage, and maps non-message activity to progress. Agent-message updates and completion remain partial snapshots; only the subsequent `turn.completed` confirmation projects the latest completed agent text as final. A missing completed message, malformed/truncated JSON, unsupported event or oversized line fails with a closed classification and no raw payload.

`AiAttemptController` is the only owner of attempt/generation state. A concurrent start is rejected; every later explicit start increments both counters, and every prior token stays stale permanently. Current events must be exactly ordered from sequence one. Duplicate/out-of-order input produces a failed terminal candidate; duplicate final, final-after-final, events after error/cancel and old-generation late output cannot mutate current state. `endInput` without final/error produces `incomplete_stream`. Task 13.9 may connect cancellation and lifecycle triggers to this controller but must not implement another retry/generation state machine.

The controller enforces explicit caller limits below repository ceilings: 2,621,440 UTF-8 bytes per raw/projected event, 16 MiB total projected bytes, 4,096 events, and 1 MiB retained partial content. Final content additionally passes the Task 13.7 contract's at-most-1-MiB limit and strict local validation. Progress/partial produce an immutable `checkpoint_candidate`; valid final, provider error, cancellation, incomplete input, sequence violation or resource exhaustion produce an immutable `terminal_state_candidate`. These are Main-memory values only, not `JobCheckpoint` or Job state. Task 13.8 creates no Job, AnalysisModuleInstance, migration, SQLite/Library write, durable recovery or resumable claim.

Default Task 13.8 tests use recorded SDK-shaped lines and injected pure state; they are offline, deterministic and authentication-free. The production utility still rejects messages fail-closed, and all Codex adapter capabilities remain false because the projector/controller are not wired to an executable request or handle. Fresh Windows certification evidence separately rebinds the compatibility and artifact fingerprints after the production-protocol change; it does not convert fixtures into runtime malformed/late-event evidence and does not establish macOS behavior.

### Task 13.9 Lifecycle, cleanup and explicit retry

`AiAttemptLifecycleService` composes the existing `AiAttemptController`; it does not own attempt or generation counters. The initial attempt and every later retry require separate explicit calls. Concurrent starts/retries are rejected, the first termination trigger is single-flight, and a bounded timeout requests termination without automatically creating another attempt. Events received after termination begins cannot mutate state. A completed/failed stream candidate is withheld until cleanup finishes; forced or unverified cleanup overrides it with a closed failure candidate.

The Codex-private lifecycle protocol admits only exact, correlated `ai.abort` and `ai.shutdown` utility messages containing an application token and closed trigger. It contains no prompt, path, PID, raw error or provider payload. Cleanup proceeds through abort observation, execution settlement, shutdown acknowledgement and actual utility exit. Only an ownership-proven live utility may enter the force-kill fallback, and every path ends in a bounded residual utility/CLI scan. Missing evidence is `unverified`, never inferred success.

`AiRuntimeLifecycleRegistry` pauses admission before it snapshots Library replacement, window close or app quit work and fans termination into all tracked active sessions. Attempts arriving after close begins are rejected, and active or quarantined participants cannot unregister out of lifecycle ownership. Main waits for cleanup alongside existing Job/structure/source-import lifecycle work and reports a window-close cleanup failure only as a static sanitized code. All cleanup observations and checkpoint/terminal candidates remain in Main memory. No AI IPC, Job, checkpoint, AnalysisModuleInstance, migration, SQLite/Library write, durable recovery or resumable state is introduced.

The deterministic production-utility smoke uses the shared Vite configuration and two independent hidden Electron processes. One proves fail-closed exit 28 for unsupported input; the other proves a valid lifecycle-only shutdown acknowledgement followed by exit 0. The installed network guard must report zero attempts, and no SDK client/turn or authentication is used. The separate Windows packaged no-Git synthetic probe is rerun only after compatibility drift and retains its own provenance. It does not prove a real production lifecycle execution; that packaged runtime gate remains Task 13.11. Adapter capabilities therefore remain false.

Task 13.9 review remediation makes the pre-execution boundaries fail closed under adversarial inputs. `CodexStreamEventProjector` receives explicit raw byte and frame budgets and charges them before JSON parsing, so ignored provider fields cannot bypass the application projected-byte budget. Structured-output contracts reject every known Zod rewrite surface (coercion, default, catch, prefault, pipe/transform, readonly and overwrite checks) and also require parsed JSON to equal validated output.

Auth storage exposes a read-only application memory. Its write capability is owned by `CodexAuthObservationAuthority`, which accepts only the strict actual-runtime input union before applying the fixed provider-neutral mapping. A TypeScript AST/import gate covers all of `src/main` and rejects any other production importer of the authority factory; `@internal` comments or forgeable structural receipts are not security boundaries. `AiAttemptLifecycleService` constructs its controller privately and publishes terminal settlement only through the cleanup-completed lifecycle outcome. Its idle promise begins with the attempt and resolves only after positively safe cleanup. Unverified cleanup remains quarantined: retry and Library replacement fail closed rather than opening another generation. A utility exit is graceful only when shutdown was acknowledged and exit code/signal proves a clean exit; abnormal exit remains unverified even when the utility sent an acknowledgement first. If timeout scheduling throws or returns an invalid cancellation handle, start returns a sanitized failure and immediately enters the same cleanup/quarantine path rather than leaving a live attempt without a timeout.

### Task 13.10 Errors, usage, diagnostics and release limits

The application owns five stable AI error codes: `AI_AUTH_ERROR`, `AI_RATE_LIMITED`, `AI_SCHEMA_INVALID`, `AI_NETWORK_UNAVAILABLE` and `AI_RUNTIME_UNAVAILABLE`. A branded failure observation must come from the composition-owned authority before it can become a `DomainError`. Auth, rate and network observations require a structured runtime discriminant; schema failure is local validation; every unknown SDK/CLI failure remains runtime unavailable. The current Codex authority deliberately exposes only local-schema and unknown-runtime producers and never classifies an English message.

Usage crosses the provider boundary only as `reported` or `unknown`. Reported usage requires exact non-negative safe-integer input, cached-input and output token fields; absence, extra fields or invalid values produce unknown. The application never inserts zeros, derives a total, prices tokens, estimates cost or performs budget confirmation. Usage may accompany an in-memory successful terminal candidate but is not persisted.

`AiDiagnosticLog` is a maximum-256-entry in-memory ring containing only frozen closed records. It accepts no free-form prompt, response, error, path, environment, credential or provider identifier field and has no filesystem, console, network or remote telemetry behavior. `config/block13-release-limitations-v1.json` separately records platform, clean-machine, signing/notarization, Defender, proxy, certificate, firewall, offline, telemetry and redistribution constraints. No Task 13.10 surface adds IPC, Job/checkpoint writes, SQLite, automatic retry or a product execution path.

### Task 13.11–13.12 packaged runtime and explicit Settings check

Task 13.11's dated Windows development-machine artifact proves only its recorded product Main, launcher, utility, success/cancel/timeout and cleanup boundary. It does not permanently authorize later builds. The build-time compatibility evaluator independently fingerprints supply chain, production protocol and probe artifact inputs; changing any relevant product AI, typed IPC, preload, Settings or build-authority source makes the prior runtime observation unusable. Source freshness alone cannot certify artifact bytes.

The current recertification evidence binds clean runtime HEAD `4e3f642fb10bb83b8df25ad613fb9de9e7c9c856` to compatibility fingerprint `60686dea87505dbf45845daf4657c1738e455b43d4258e71617fe698c9c56e92`. The product artifact passed isolated success, cancel and timeout, the separate certification artifact passed all 17 no-global-Git assertions, and the normal packaged Settings path passed all 16 visible-entry, connection, observation, cleanup and residual assertions. An ordinary build embeds stale compatibility. An explicit certification build may embed the current source fingerprint. Runtime accepts the external receipt only when its fingerprint, ordered file sizes/hashes, aggregate receipt hash, and streamed SHA-256 checks of the exact packaged executable, `app.asar` and pinned Codex executable all agree. Missing, malformed or mismatched receipt is stale and erases auth observation to unknown. The receipt proves byte equality only; without a signing key or trusted OS signature it is not a cryptographic proof that a probe ran or passed. Main-thread acceptance of separately authorized product, no-global-Git and Settings natural-path evidence remains the probe-provenance authority. The successful Settings observation is transient Main memory and restart begins unknown. Default packaged E2E remains offline and never clicks the real connection action.

Forge packaging is platform-conditional. Windows x64 resolves and packages the pinned Codex SDK/CLI/platform runtime plus the production utility. A non-Windows Forge configuration remains loadable for non-AI development and packaging, but does not include the Codex utility or Windows runtime package; macOS AI compatibility remains blocked/deferred rather than crashing the whole application configuration.

The product packaged-probe result writer accepts only a UUID-owned directory created atomically beneath the canonical OS temp root. It rejects an existing run path, symbolic link, junction or reparse substitution, then pre-opens `result.json` exclusively with owner-only permissions before the probe begins. Final bytes are written and flushed through that stable file handle; directory and file identity are checked before and after publication. This prevents a path swap from redirecting the result bytes, but it is not a security boundary against a same-privilege process that can tamper with the installation or temporary storage; such a process can still cause denial of service.

Task 13.12 adds exactly one product channel, `ai:check-connection`. Its request schema is strict `{}` and its response contains only provider-neutral Gate, compatibility and runtime/auth observation fields. `config/block13-ai-gate-v1.json` is the single versioned application Gate authority; `src/shared/contracts/ai-gate.ts` validates it strictly and projects the same frozen value to Main and renderer. The release-limitation matrix references that authority instead of copying its verdict. Compatibility is injected from the build fingerprint; auth/runtime observation is ephemeral Main memory with `observedAt`. These layers never overwrite one another.

Settings starts no check on application startup, render, Library open or navigation. Only the visible button invokes the fixed short synthetic utility request. The renderer has no prompt, schema, SDK, filesystem, process, token or raw IPC surface. Only an admitted check clears the previous displayed/runtime observation; paused, concurrent, quarantined or failed admission preserves the last still-valid result. The application service delegates admission, attempt/generation, timeout and cleanup to the existing `AiAttemptLifecycleService`/`AiAttemptController`; concurrent checks do not create another generation. Library replacement and window close invalidate observation before lifecycle termination, and a Settings component that unmounts ignores its late IPC response.

Scratch workspaces are private random directories created directly beneath a realpath-validated OS temporary root. Creation and cleanup both revalidate the owned directory and reject link/reparse substitution before removal. Window, Library and shutdown admission pauses are independently reference-tracked; a macOS replacement window resumes only its window-close reason after the prior cleanup barrier settles. Ownership-proven force termination treats `kill() === false` as immediate unverified failure, bounds the exit wait after an accepted kill and releases lifecycle listeners when exit cannot be observed.

The Codex-private utility owns the fixed input and strict one-field schema, uses an OS-temp non-Git scratch directory with `skipGitRepoCheck=true`, and emits only `authenticated` or `runtime_unavailable`. It does not infer login-required, expiration, permission, network or rate classifications from messages. Main promotes authenticated only after strict output and graceful cleanup under the same fresh fingerprint. All other or stale cases remain unknown/runtime-unavailable as defined by D104.

Observation is never written to Library SQLite, Job, checkpoint, export, log or credential storage. Restart begins unknown; fingerprint drift immediately invalidates prior observation; time passage alone does not refresh it, and no TTL is invented. AI generation actions remain disabled. Default unit/integration/UI tests inject transport and remain offline; a real packaged check is never part of `npm run check`.

### Future Block 14–18 inference governance boundary

The production analysis design uses a bounded inference-governance protocol rather than a universal literary ontology or a stored model chain of thought.
The sole detailed cross-module production-quality authority is
`docs/engineering/V1-BLOCK-14-SYSTEM-PRODUCTION-QUALITY-GATE.md`, currently
`USER_CONFIRMED_DIRECTION / REV3.2_CONFIRMED / BLOCK14_NOT_FROZEN / QUALITY_UNPROVEN`.

The common semantic relationship is:

```text
EvidenceAnchor -> textual fact / grounded observation
               -> material interpretation alternatives
               -> current assessment or unresolved
               -> derived conclusion and downstream dependencies
```

These are semantic layers first. They do not imply one SQLite row, table or separately addressable object for every fact, observation, interpretation and conclusion. Ordinary textual facts and non-authoritative reading prose may remain inside a module-specific payload or Markdown body. A complete `InferenceReviewRecord` is required only when an interpretation is user-reviewable, crosses module boundaries, participates in a Perspective, Technique candidate, AI constraint or export, or affects completion and invalidation.

The common record contract must carry enough structured information to validate:

- the question/subject and exact Book/scope/text or character-stage applicability;
- grounded observations and their EvidenceAnchor mapping;
- material alternative interpretations;
- an ordinal support classification such as direct, strong inference, weak inference or hypothesis;
- a selected current assessment or explicit unresolved result;
- a concise audit rationale, counterevidence/conflict facts and disconfirmation conditions;
- explicit upstream and downstream dependency references.

This is an audit summary, not private model reasoning. Block 17 must not request, persist or export hidden step-by-step chain-of-thought. Prompt composition is versioned and layered as a short common protocol, the current module/scope focus card, the strict output schema and a small number of targeted examples. It must not concatenate the complete methodology library or all module examples into every SDK turn.

Module-specific payload schemas retain open literary interpretation. The common protocol only governs evidence, scope, uncertainty, alternatives, correction and participation. Gate 14-G0 is closed with seven core modules: Story Plot, Narrative Orchestration, Characterization, Relationship Dynamics, World Setting, Language/Style and Theme/Meaning. D131 closes Story Plot's endpoint/ownership patch as `DOMAIN_SEMANTICS_CLOSED / PRODUCTION_CONFIGURATION_OPEN` and progress `1 / 7`; the other six reviews and all shared evidence/review/deep-payload contracts remain open. Block 17 executes only a fully frozen result through the production Job/prompt/schema pipeline; Block 18 owns persistence, user correction, history, diff, semantic dependency propagation and completion gates.

The seven modules currently present in the shared contract, migration seed, module workbench and tests are a different compatibility baseline, not the approved product ontology. The 14-G1 impact inventory now covers canonical keys/order, migration 003 and downstream migrations, module instances, workspace/completion gates, TypeLibrary/configuration snapshots, `inputModuleKeys`, tests and compatibility fixtures. Its status is `IMPACT_ASSESSMENT_COMPLETE / IMPLEMENTATION_ADMISSION_OPEN`; canonical keys, shared contracts and migration strategy remain undecided, and those changes may not be hidden inside a deep-payload-schema task.

Scope is not an ownership container. Canonical events, characters, relationships, rules and language observations retain stable identities across chapter, story-segment, volume and Book views; a higher scope may add only a reference-based synthesis. Scan, candidate, formal-asset and synthesis eligibility replace whole-module completion prerequisites. Routed candidates remain non-authoritative until resolved by their domain owner.

`TextRange` remains a generic and potentially overlapping interval. Gapless scan accounting uses the
separate logical `CoverageSliceRevision`, bound to one source edition and coverage-plan revision. Active
core ranges under one plan are gapless and non-overlapping; optional halo ranges may overlap but earn no
coverage credit. A slice stores references and run metadata only, owns no literary asset and is not an
AI-call boundary. Block 17 owns call splitting, batching and context reuse. A coverage-plan change may
replace slice revisions without changing canonical asset identity.

`AnalysisModuleInstance` owns run/input-version records, module-body revision, asset references, status
projection and genuine Scope synthesis. Canonical assets and EvidenceAnchors remain with their domain
owners and do not become instance-owned copies. This is a logical responsibility boundary; physical
table topology and migration remain open.

Story Plot has four canonical asset kinds: `StoryEvent`, `EventRelation`, `Plotline` and
`PlotlineRelationClaim`. `PlotlineDevelopmentRecord` single-writes event-to-line meaning;
`PlotlineLifecycleRecord` alone writes open/pause/resume/reopen/close transitions. Deterministic Scope
projection is non-authoritative and `StandardStoryRecap` is a sourced derived asset, not a fact store.

All detailed Story Plot semantics—including relation families/endpoints, admission, lifecycle, required
recap-focus disposition and production experiment design—are single-sourced in
`docs/engineering/V1-BLOCK-14-STORY-PLOT-CROSS-EXAMINATION-RECORD.md`. This document records only
architectural ownership and status. These remain logical boundaries, not admitted TypeScript/Zod,
persistence or IPC shapes.

Block 16 alone owns formal Technique observations, abstractions and reusable candidates. A module-external constraint-governance domain alone owns formal AIConstraint candidates, provenance, applicability, strength, conflicts, review and versions; the summary page is read-only. Block 17 owns call topology, batching and context reuse but cannot redefine these owners through Prompt composition. Block 18 must persist asset/conclusion dependency indexes and propagate stale selectively rather than invalidating an entire module merely because a source or structure version changed.

Module completion proves that a bounded focus surface was checked, not that literary analysis is exhaustive. Checked-empty, not-applicable, insufficient-evidence and unresolved can be honest terminal outcomes, but only qualified results may satisfy downstream or publication gates. MainType Base and ordered ContentFocus Overlays may change attention, thresholds and methods; they cannot alter the seven-module ontology or fact ownership.

A future continuation-context brief is a downstream read model, not an AnalysisModule or Story Plot write model. Its deterministic projection selects stable, versioned references to the current situation, active/unresolved PlotLines, recent key choices, relevant Character/Relationship/World states, outstanding promises/setups and source locations. Merely viewing it performs no AI call. Block 17 may generate only the compressed expression over that projection; the generation records dependency versions. Block 18 persists versions and dependency facts, marks only materially affected generations stale and exposes explicit/pre-continuation refresh. The later Original-writing domain owns continuation actions. Block 14 only freezes source eligibility, reference identity and invalidation conditions.

Book-specific focus questions are a future additive analysis-configuration input. Before first formal analysis, a Book may freeze an ordered zero-or-more question set; each question is natural language with optional approved-module and supported-scope routing. The set changes no domain Schema or ownership and cannot substitute for standard focus cards. Block 17 composes eligible questions into existing analysis batches without a mandatory second full-Book pass. Block 18 owns future persistence, dependency history and selective rerun impact. Exact question DTO/table topology is unadmitted. Separately, the current mutable TypeLibrary binding and later-edit CAS path conflict with the product rule that a confirmed MainType/ContentFocus selection is permanently frozen; that transition requires a dedicated Block 12 compatibility and admission decision.

Run/coverage status, epistemic support and review/authority are three independent axes. Failure, retry,
deferred, overflow and coverage-risk are runtime meanings; insufficient-evidence, competing and
unresolved are epistemic meanings; review and consumer admission are authority meanings. No value on one
axis may silently satisfy another. Internal `confirmed + analysis_inference` means only that an inference
passed its review gate; renderer and export language must present it as a supported/accepted
interpretation, never as a confirmed textual fact. User acceptance of a correctly represented
hypothesis does not convert it into a fact.

Book progress has two semantics: `AnalysisCoverageComplete` for successful required source coverage and
honest finite-focus disposition, and `AuthorityReviewComplete` for explicit disposition of the current
authority-review set. Neither is a global downstream-admission flag. Perspective, Technique-source,
AIConstraint, export and other consumer eligibility is calculated per asset and consumer policy.
Structured assets are not all mandatory review; unreviewed or unresolved assets gain no authority
automatically.

Prompt content budget uses priority B: minimum Base coverage, correctness triggers, user-ordered
Book-specific focus, ordered ContentFocus Overlays, then optional literary deep dives. Programmatic
safety and contract enforcement stay out of Prompt content budget but remain inside total cost, latency
and failure-rate hard limits.

Invalidation is split into two algorithms:

- **configuration invalidation** derives impact from immutable TypeLibrary, Methodology, Prompt, Schema and composition snapshot differences under the versioned analysis-configuration diff authority;
- **semantic dependency invalidation** follows actual dependency references after a user changes evidence, an observation, an interpretation or a conclusion.

Semantic impact may not be caller-declared and may not reuse the configuration diff algorithm. Both paths preserve history and mark downstream assets stale or in need of review; neither silently rewrites confirmed content.

Block 14 may admit only separately authorized pure contracts, reference algorithms and deterministic
fixtures after the logical baseline closes. It may not bring forward a production Job, SQLite queue,
persistence topology or review UI. No migration, Evidence/Relation/Inference table, repository, service,
IPC, renderer editor, real Prompt, SDK analysis turn or AI result persistence is admitted by this design
correction. Their admission remains with the owning Block 14–18 tasks.

Migration 005 adds admitted placeholder columns to `analysis_module_instances`; it does not create speculative evidence, relation, Technique, perspective, export, Prompt, or snapshot tables. Technique production tables remain unadmitted until identity, producer, immutable `SourceSnapshot` capture transaction and real read/write lifecycle are separately approved.

The Block 14 inference-governance design is not an implicit schema admission. Its four semantic levels do not reserve four table families, and `InferenceReviewRecord` remains a product/contract concept until Block 14 freezes its bounded schema and a later table-admission task proves ownership, identity, lifecycle, read/write paths and migration witnesses.

Version fields:

- `source_text_edition`: source content, encoding normalization or source correction.
- `structure_edition`: title tree, chapter boundaries and story range changes.
- `analysis_revision`: module body edits, rerun acceptance and structured analysis changes.

Migration rules:

- All schema changes go through numbered SQL migrations.
- App startup runs pending migrations in a transaction after backing up or snapshotting the database according to the migration policy.
- Migration startup validates applied migration id/name history against the static migration registry. Unknown future migrations and id/name mismatches must reject open before pending migrations run.
- applied migrations must be a contiguous prefix of the static registry; a database with migration 2 applied and migration 1 missing is invalid.
- Failed migration leaves the original database usable or explicitly marks it blocked with a recoverable reason.

| `TypedIpcBridge` | Shared renderer-to-main contract and runtime validation |

Service rules:

- Renderer calls services only through typed IPC.
- Services return domain errors with stable codes.
- Services never return raw SQLite rows directly to renderer.
- Structure detection runs receive a positive per-book `run_sequence` inside the aggregate write transaction. Latest-run, active-run, recovery, and manual-fallback authorization order only by this persisted sequence, never by wall-clock timestamps or UUID text.
- Structure freeze invokes the synchronous DB-only `StructureEditionChangePort` inside its aggregate transaction. The port emits `needs_rebuild`/`stale`/`needs_refresh` plus a non-persisted future CompletionGate invalidation instruction; it never starts downstream work.
- Analysis configuration changes and semantic corrections use separate future invalidation ports. Configuration impact is derived from immutable configuration snapshot differences; semantic impact follows stored dependency references from changed evidence/observations/interpretations/conclusions. Neither port may accept a caller-invented affected-module list.
- Long work emits job progress instead of blocking request IPC.
- `LibraryService.create` is the only flow allowed to create `writestorm.sqlite`; it requires an absent or empty library root and must not adopt an existing database without a valid create flow.
- `LibraryService.open` requires both `manifest.json` and `writestorm.sqlite`; it must not recreate a missing database for an existing library.

## 10. Job and Checkpoint Design

The executable state vocabulary and transition graph are owned by
`src/shared/domain/job.ts`. The current graph is:

```text
queued -> estimating | running | failed | cancelled
estimating -> waiting_confirmation | running | failed | cancelled
waiting_confirmation -> running | cancelled
running -> paused | failed | cancelled | completed
paused -> running | cancelled
failed -> resumable
resumable -> running | cancelled
cancelled -> terminal
completed -> terminal
```

Checkpoint units:

| Job type | Unit | Current implementation |
| --- | --- | --- |
| `source_import` | source copy + metadata | Implemented |
| `structure_detection` | structure draft | Implemented |
| `structure_edition` | structure edition | Implemented |
| `analysis_module_shell_creation` | module instance batch | Implemented |
| `analysis_module_instance_analysis` | module instance batch | Contract only; not creatable |
| `export` | export manifest and blocked reason | Contract only; not creatable |

Rules:

- `Job` state is separate from `Book` state and `AnalysisModuleInstance` state.
- Final completion checkpoints are committed through the owner transaction, not through the generic
  transition API.
- Source-import and structure-detection runtimes must stop and clean up before cancellation is persisted.
- Resume remains disabled for implemented Job types. Contract-only AI analysis and export vocabulary
  does not establish a runtime producer, recovery path or executable product action.
